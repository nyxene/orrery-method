## Что поставляет привязка {rule}

Трекер может связать метод, только если поставляет всё перечисленное; чего он не даёт, привязка заявляет как отсутствующее, а не подменяет приблизительным.

```spec Привязка поставляет
Containment — feature, владеющая своими tasks, с выводимым из этого rollup.
Контейнер release — именованный набор, которому item принадлежит, закрываемый и не требующий дат.
Закрытие мержем — пулреквест закрывает свою task без второго акта.
Связи зависимости — нативные, запрашиваемые, снимаемые закрытием блокера.
Зеркальная ссылка — ссылка в теле одного item появляется на его цели, чтобы провенанс читался в обе стороны.
Оси — дом для type, area, priority и flags, который агент умеет читать и писать.
Дом для review mark — единственному факту, который метод не выводит, нужно место, работающее на дозапись; это файл в репозитории, а не объект трекера.
Запись, переживающая работу — evidence package и его вердикт остаются читаемыми на закрытом item, потому что именно там независимость показывается постфактум.
```

Primitive, который метод не использует, остаётся нетронутым, а не приспосабливается. Неиспользуемое поле не стоит ничего; приспособленное тащит чужую семантику в каждый запрос, который его читает.

## Две привязки целиком {rule}

Эти две выписаны объект за объектом, потому что всё после них излагается отличием от одной из двух. Каждая строка закрепляет один объект за одним нативным primitive, и проект на любом из этих трекеров использует колонку как написано.

| Объект | GitHub | Jira |
|---|---|---|
| Feature | Issue, `type/feature`, sub-issues | Epic |
| Task | Sub-issue, один пулреквест, `Closes #N` | Story, один пулреквест, переход на мерже |
| Flat item | Issue без родителя и без milestone | Story, Bug или Task без Epic и без fixVersion |
| Release | Milestone | Version — выпускается актом, даты оставлены пустыми |
| Evidence package | Комментарий к issue | Комментарий к issue |
| Ledger | Файл в репозитории — объекта трекера нет | Файл в репозитории — объекта трекера нет |
| Зависимость | Связь `blocked-by` | Связь `blocks` |
| Ось type | Метки `type/` | Issue type |
| Ось area | Метки `area/` | Component |
| Ось priority | Метки `priority/` | Поле Priority |
| Flags | Метки `flag/` | Labels |
| Прогресс feature | Rollup по sub-issues | Прогресс Epic |
| Review mark | Файл в репозитории, дозаписываемый раз в проход чтения | Файл в репозитории, дозаписываемый раз в проход чтения |

Эти две выписаны потому, что на них уже стоит большинство проектов: на одном живёт код, на другом живёт работа. И вдвоём они покрывают обе формы, какие принимает трекер, — все оси в метках либо каждая ось в своём поле, — так что третья колонка повторила бы *файл в репозитории* ещё четыре раза и утопила бы горстку ячеек, где действительно есть разница.

Всё, что идёт после, изложено отличием, и каждая привязка открывается тем, какую колонку читать.

| Привязка | Читать | И ожидать |
|---|---|---|
| GitHub | — | Самая распространённая; выведена, как и остальные |
| Jira | — | Закрытию нужен настроенный переход; блокирующая связь переживает свой блокер |
| GitLab | GitHub | Containment и зависимости — платные возможности; ниже этого тарифа она не связывает |
| Azure DevOps CMMI | Jira | Бо́льшая часть платформы намеренно не используется |
| Linear | GitHub по закрытию, Jira по осям | Cycles — это таймбокс, они остаются неиспользованными |
| YouTrack | Jira | Смоделирует что угодно, включая метод неправильно |

## GitHub {rule}

На GitHub каждую ось несёт метка. Это вынуждено, а не выбрано: структурный primitive типа существует у платформы только для организаций. На личном аккаунте нет альтернативы, которую умел бы прочесть токен автоматики, — поэтому дисциплина меток здесь структура, а не гигиена; если репозиторий когда-нибудь переедет в организацию, миграция механическая: прочесть у каждого issue его единственную метку `type/`, проставить тип, метку удалить.

Привязка поставляет именование, которого сами оси не предписывают: `axis/value`, нижний регистр, дефисы между словами, существительные в единственном числе. Префикс делает оси видимыми агенту, читающему плоский список меток, и проверяемыми сравнением строк, а каждая метка внутри оси носит один цвет — две фишки одного цвета на одном issue значат нарушенную эксклюзивность, читаемую с одного взгляда на каждой оси, кроме flags, чьи члены цвет делят законно. Дефолтные метки платформы удаляются до того, как заведён первый issue: каждая из них — второй дом для значения, которое оси уже несут, записанный голым словом.

Всё остальное нативно. Sub-issues несут containment и rollup, `Closes #N` и связанная ветка одинаково закрывают task на мерже, связи зависимости снимаются при закрытии блокера, а очередь готового — это поиск открытого и незаблокированного.

Байты release — это то, что `main` держит на его теге: членство в milestone записывает обязательство, а changelog выводится из мержей между двумя тегами. Строке `Origin: #N` у bug не нужно никакой машинерии: платформа зеркалит каждую ссылку из тела на таймлайн цели, так что страница feature несёт собственную после-историю без просьб.

## Jira {rule}

Там, где GitHub кладёт каждую ось в метку, Jira даёт каждой своё поле: issue type несёт type, Component несёт area, Priority — отдельное поле, а метки остаются одним лишь flags. Нет ни соглашения об именовании, которое надо держать, ни цвета, который надо читать, — платформа проводит одно значение на поле, без всякой просьбы.

Один primitive здесь лучше всего, что есть в этом документе. **Version — это release ровно в том смысле, в каком его определяет метод**: именованный набор, которому item принадлежит, выпускаемый актом и не несущий дат, пока их кто-нибудь не добавит. Любой другой привязке в этой строке нужна оговорка про время; этой — не нужна.

Containment предлагает три уровня там, где метод использует два. Epic владеет Story, Story владеет Sub-task, и метод останавливается на первой паре: feature — это Epic, её tasks — это Stories, а Sub-task остаётся неиспользованным, как и всякий primitive, который методу не нужен.

Две вещи эта привязка заявляет как отсутствующие, а не подменяет приблизительным.

**Закрытие не одним актом.** Платформа не закрывает issue, когда вливается пулреквест; чтобы это делалось, надо настроить переход. Пока такой автоматики нет, мерж и закрытие — два акта, и второй из них есть чьё-то «вспомнил», то есть ровно тот сбой, который метод называет везде. Привязка неполна, пока переход не смонтирован, и проект, который его не смонтировал, этой привязки не имеет.

**Блокирующая связь переживает свой блокер.** Связь остаётся после закрытия блокера, поэтому очередь готового не может быть простым запросом «открытое и незаблокированное»; она — открытое минус то, чьи блокеры ещё открыты. Факт восстановим, а запрос длиннее на одно условие, — но это запрос, который другим привязкам не нужен, и он заявлен здесь, а не обнаруживается потом.

## GitLab {rule}

Читайте колонку GitHub и почти ничего не меняйте. `Closes #N` в merge request закрывает свой issue на мерже, milestone несёт release, метки несут оси с тем же именованием `axis/value`, а упоминания зеркалятся на цель.

Различается не форма, а тариф. **Epics, блокирующие зависимости и scoped labels — платные возможности.** Это бьёт неравномерно:

- Без epics над issue нет containment, и двум живым уровням метода негде стоять. Чеклист внутри issue containment не является: он не производит ни дочернего item, ни rollup, ни чего-либо, что найдёт запрос.
- Без блокирующих связей зависимость снова становится прозой — тем самым, что метод заменил связью именно потому, что проза не запрашивается.
- Scoped labels — то, что платформа умеет проводить сама; без них эксклюзивность на оси есть дисциплина, ровно как на GitHub.

Так что на бесплатном тарифе эта привязка заявляет два из восьми как отсутствующие, а две нехватки — это не привязка. На тарифе, который их несёт, GitLab связывает метод так же полно, как GitHub, и scoped labels делают его строже: платформа сама отказывает во втором значении на одной оси, вместо того чтобы оставлять это цветовому соглашению.

## Azure DevOps CMMI {rule}

Читайте колонку Jira: у осей и здесь нативные дома. Area растворяется в Area Path, priority — в поле Priority, и теги нужны только type и flags, так что дисциплина меток ужимается тем же способом и по той же причине.

Различаются две строки. Task — это Requirement, закрываемый через `AB#` в пулреквесте, то есть закрытие одним актом, как у GitHub и в отличие от Jira.

Iteration Path служит release с пустыми датами: платформа читает итерацию как таймбокс, а метод прогнозирует в токенах, так что дата утверждала бы то, чего никто не измерял. Version у Jira в такой инструкции не нуждается.

CMMI приходит с бо́льшим количеством машинерии, чем метод потребляет, — Change Request, Risk, Review, поля оценок, машина состояний со стадией Resolved. Всё это остаётся неиспользованным, и это определяющая черта привязки, а не сноска: состояние здесь выводится, как и везде, rollup отвечает на прогресс, и ничья рука не двигает work item по доске.

## Linear {rule}

Читайте GitHub по закрытию и Jira по осям. Влитый пулреквест закрывает свой issue через нативную интеграцию, а priority — поле, а не метка, как в Jira.

Единственное, что важно не упустить, — release. **Cycle — это таймбокс, а метод не прогнозирует во времени**, поэтому Cycles остаются неиспользованными, и release несёт Project. Не сказать этого — способ, которым проект начинает планировать двухнедельными отрезками внутри метода, считающего в токенах, ни разу этого не решив.

Всё остальное ложится чисто: sub-issues несут containment и его rollup, блокирующие отношения нативны и запрашиваемы, комментарии переживают работу, а API — путь записи, который агент может держать. Из четырёх привязок, изложенных здесь, эта требует меньше всего оговорок.

## YouTrack {rule}

Читайте Jira и ждите ту же форму, но с большей долей настраиваемого: оси — кастомные поля, так что type, area, priority и flags получают по полю вместо общего пространства меток, а release несёт поле вроде Version.

Эта настраиваемость и есть предостережение. **Трекер, который смоделирует что угодно, позволит проекту смоделировать метод неправильно** — пятая ось, поле статуса, оценка в часах, — и ничему из этого не откажет. Набор значений и восемь инвариантов здесь вся охрана; платформа не поставляет ничего из неё.

Закрытие едет на командах в коммитах и интеграции с VCS, что ставит его в то же положение, что у Jira: оно работает, и оно настройка, а не свойство платформы. Привязка неполна, пока этой настройки нет.

## Что стоит за каждой из них {guide}

Шесть привязок, выложенных таблицей, читаются как шесть проверенных устройств. Они не таковы, и сказать это там, где читатель с ними встречается, стоит одного абзаца.

**Ни одна привязка не запускалась, потому что ни один проект пока не работал по этому методу.** Все шесть выведены одинаково: из того, что каждая платформа документирует о собственных primitives, сверенного с восемью требованиями и больше ни с чем.

**Порядок на этой странице — распространённость, и ничего кроме.** GitHub идёт первым потому, что читатель вероятнее всего уже там; Jira стоит рядом в полной таблице потому, что там уже держит работу большинство проектов. Ни одна позиция не утверждает, что привязка изучена лучше, — обе не проверены одинаково, вместе с четырьмя следующими.

Их standing — `Pending`, как и у корпуса, который их несёт. Первый проект, который любую запустит, найдёт то, чего эта страница не говорит, — и когда найдёт, место finding — здесь, на привязке, и заводится, как всякий другой дефект.
